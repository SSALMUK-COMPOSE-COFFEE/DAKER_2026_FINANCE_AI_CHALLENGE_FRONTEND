## 0. 결론 먼저 — LLM은 두 군데서만 씁니다

| 단계 | 누가 | 왜 |
|---|---|---|
| 자유 서술 → **축 4개 추출** | LLM (structured output) | 문장에서 값을 뽑는 일은 룰로 못 함 |
| 축 4개 → **유형 확정** | **룰 테이블** | 유형지도에 판정 매핑표가 이미 있음 |
| 유형 → **근거 텍스트 선택** | **DB 조회 (키 1개)** | 유형이 16개뿐. 검색이 필요 없음 |
| 근거 + 사실관계 → **소명서 문장** | LLM | 이것만이 생성이 필요한 일 |
| 리스크 판정 (도박·환치기·대리송금·접근매체) | **룰, LLM 금지** | 오판 시 자기부죄 문서가 나감 |

**유형 판정을 LLM에 맡기지 않는 이유.** 같은 입력에 같은 유형이 나와야 디버깅이 됩니다. 그리고 T12(도박 환전)를 T1(실물 중고)로 잘못 분류하면 **도박죄 자수 문서를 만들어 주게 됩니다.** 이건 확률적으로 맞히면 되는 종류의 일이 아닙니다.

### 1-3. 임베딩과 태그 매칭을 같이 씁니다

기존 스키마는 `document_chunks`에 임베딩을 두는 **RAG 설계**이고, 작업분해는 **태그 매칭**으로 정했습니다. 둘 다 씁니다. 쓰는 자리가 다릅니다.

| 경로 | 방식 | 이유 |
|---|---|---|
| **소명서 생성** | `snippet_packs` 키 조회 | 유형이 16개뿐. 검색할 이유가 없고, 캐시가 살아남 |
| 원문 근거 찾기·유사 사례 | `document_chunks` 임베딩 | 원문이 수백 건이라 여기서만 검색이 값어치를 함 |

**소명서 경로에 임베딩을 쓰면 안 되는 이유가 하나 더 있습니다.** 검색 결과가 매번 달라지면 **같은 사람이 두 번 돌렸을 때 다른 소명서가 나옵니다.** 그리고 어느 근거가 들어갔는지가 호출마다 바뀌어서 출처 표기의 신뢰가 무너집니다.

## 2. 빌드 타임 — 지금 C가 하는 일

```
수집 원문                사람이 유형 코딩          섹션별 요약            유형별 조립
case_example  ──────▶  type_code 부여  ──────▶  case_digest  ──────▶  snippet_pack
   (원문 보존)           (판정 매핑표 기준)        (검수 플래그 필수)      (토큰 예산 검사)
```

**1) 원문은 반드시 남깁니다.** 요약만 저장하면 나중에 "이 문장 근거가 뭐냐"에 답을 못 합니다. 소명서 전 문장에 출처를 표기하는 것이 이 서비스의 핵심 주장이라, 원문 없이는 그 주장이 무너집니다.

**2) 유형 코딩은 사람이 합니다.** 유형지도 6-3이 *"필자가 제목·요약·본문을 읽고 부여한 코딩 결과"*라고 이미 밝혀 뒀습니다. GPT에 초벌을 시키되 **최종 확정은 사람**이고, `verified` 플래그가 false인 digest는 pack에 넣지 않습니다.

**3) digest는 5개 섹션으로 씁니다.**

| section | 무엇을 적나 | 소명서에서 쓰이는 자리 |
|---|---|---|
| `situation` | 어떤 상황이었나 (사실만) | 경위서 도입 |
| `issue` | 무엇이 쟁점이었나 | 이의제기 사유란 |
| `won` | 무엇이 받아들여졌나 | 주장 구성 |
| `lost` | 무엇이 기각됐나 | **피해야 할 서술** |
| `phrasing` | 실제로 통한 표현 | 문장 톤 |

**`lost`가 가장 값집니다.** 거래금액 21,040,000원 사건에서 21,090,000원을 청구했다가 초과분 기각 + 소송비용 1/10 부담 — 이런 건 성공 사례 100건보다 유용합니다.

**4) pack 조립 시 검사할 것 셋**
- 토큰 예산 — 유형당 pack이 과하면 캐시 이득이 사라집니다
- 빈 유형 — digest가 0건인 유형은 **LLM에 줄 근거가 없다는 뜻**이라 그 유형은 "일반 안내"로 폴백
- `in_scope=false` 유형(T12·T13·T14·T16) — pack에 **소명서 문안이 아니라 차단 안내문**을 넣습니다

## 3. 런타임 — 소명서가 나오기까지

```
[1] 문진 답 8개
      │
      ├─ 자유서술만 있으면 → LLM 축 추출 (structured output, 축 4개만)
      ▼
[2] type_rule 평가 ── 룰, 결정론적 ──▶ type_code 확정
      │
      ├─ risk_level = 'block' ─▶ ✋ 여기서 중단. LLM 호출 없음. 차단 안내 출력
      ▼
[3] DB 조회 (검색 아님, 키 조회)
      snippet_pack[type_code] · evidence_path[subject] · bank_requirement[bank]
      ▼
[4] LLM 1회 호출
      ┌ 캐시 구간 ┐ 시스템 프롬프트 → 법령 원문 → snippet_pack → 반려사유
      └ 비캐시   ┘ 사용자 사실관계(문진 답·거래내역·대화)
      ▼
[5] 소명서 3종 + 문장별 출처
```

**[2]에서 멈추는 설계가 중요합니다.** 리스크 유형은 **LLM을 아예 호출하지 않습니다.** 호출한 뒤 후처리로 거르면, 모델이 이미 만든 자기부죄 문장이 로그·스트림에 남습니다.

**[4]의 순서를 지켜야 합니다.** 변동값(사용자 입력)이 앞에 섞이면 캐시가 통째로 깨집니다. `usage.cache_read_input_tokens`가 0이면 순서가 틀린 것입니다.

## 4. GPT mock 검증 — API 붙이기 전에 혼자 할 것

서비스에 연결하기 전에 **DB 없이, 코드 없이** 먼저 확인합니다. 틀린 pack 형식으로 20개 유형을 채운 뒤 갈아엎는 게 제일 비쌉니다.

### 4-1. 3개 유형만 먼저

| 유형 | 왜 이것부터 |
|---|---|
| **T1** 실물 중고물품 | 가장 흔한 정상 경로. 여기서 안 되면 아무것도 안 됨 |
| **T4** 게임 재화 | 증거 발급처가 외부(게임사)인 대표 케이스 |
| **T12** 도박 환전 | **차단이 제대로 되는지** 확인. 코퍼스 최대 군집 |

### 4-2. 절차

1. 스프레드시트 3행으로 digest를 손으로 씁니다 (섹션 5개 × 유형 3개)
2. 그걸 이어 붙여 pack 텍스트를 만듭니다 — **이게 나중에 `snippet_pack.pack_text`가 됩니다**
3. GPT/Claude 웹에 `[pack] + [가짜 사실관계 한 벌]`을 붙여넣고 소명서를 뽑습니다
4. 아래 5개로 채점합니다

| 확인 | 불합격 신호 |
|---|---|
| **환각** | 사실관계에 없는 날짜·금액·이름이 문장에 등장 |
| **조문 오인용** | 제7조 항·호를 틀리게 인용 |
| **`lost` 회피** | 반려 사유로 적어둔 서술을 그대로 씀 |
| **출처 부착** | 문장마다 근거를 못 대고 뭉뚱그림 |
| **T12 차단** | 도박 사실관계를 넣었는데 소명서를 만들어 줌 ← **가장 중요** |

**T12에서 소명서가 나오면 그 pack은 실패입니다.** 다시 짭니다.

### 4-3. 통과하면

그 pack 형식을 **그대로 스키마로 굳히고** 나머지 유형을 같은 틀로 채웁니다. 그 다음 B에게 넘기는 것은 세 가지입니다.

- `snippet_pack` (유형별 통짜 텍스트)
- `type_rule` (문진 답 → 유형 판정 조건)
- `evidence_path` + `request_template` + `bank_requirement`

**B는 이걸 조회해서 프롬프트에 끼우기만 합니다.** C가 pack을 고치면 B의 코드는 안 바뀝니다. 이게 이 구조를 쓰는 진짜 이유입니다 — **마감 직전에 문안을 고쳐도 서버를 안 건드립니다.**

## 6. 하지 말 것

- **은행 요구서류를 추측으로 채우기** — 미공개는 `disclosed:false`로 두고 법정 필수 2종으로 대체합니다. 틀린 서류 안내가 이 서비스의 최대 사고입니다

- **유형 판정을 LLM에 위임** — 재현이 안 되고 리스크 게이트가 뚫립니다

## 7. 프론트 선택지는 C가 짭니다

**결론부터 — 선택지는 C가 짜는 게 맞습니다.** 취향 문제가 아니라 구조상 그렇습니다.

`question_options.option_key`가 **프론트가 서버로 돌려보내는 값**이자 **`type_rules.condition`이 읽는 입력값**입니다. 같은 문자열이 양쪽에 쓰입니다.

```
[화면]  "환전받은 돈입니다"  ──클릭──▶  option_key = 'exchange'
                                            │
[판정]  type_rules.condition = {"q3":["exchange"]}  ──▶  T12 (차단)
```

A가 선택지를 임의로 정하면 `'exchange'`가 `'exch'`나 `'환전'`이 되고, **룰이 매칭에 실패해서 T12가 조용히 안 걸립니다.** 차단돼야 할 사람에게 소명서가 나가는 사고가 이렇게 납니다.

### 역할을 이렇게 나눕니다

| 누가 | 무엇 |
|---|---|
| **C** | 문항 문구 · 선택지 문구 · `option_key` · 어느 축에 대응하는지 · 경고문 |
| **B** | `GET /api/questions`로 그대로 서빙 |
| **A** | 받아서 렌더링. **문구도 값도 코드에 박지 않음** |

**이렇게 하면 마감 직전에 문구를 고쳐도 배포가 필요 없습니다.** `UPDATE question_options SET label = ...` 한 줄이면 화면이 바뀝니다. 6일짜리 일정에서 이게 생각보다 큽니다 — 문안은 반드시 마지막까지 고쳐집니다.

**A에게 넘길 계약은 이 모양입니다.**

```jsonc

   "options":[
     { "key":"sale",     "label":"물건이나 서비스를 팔고 받은 대금입니다" },
     { "key":"wage",     "label":"일한 대가입니다 (급여·용역비·수수료)" },
     { "key":"family",   "label":"가족이나 아는 사람이 보내준 돈입니다" },
     { "key":"unknown",  "label":"거래한 적이 없는데 모르는 사람이 보냈습니다" },
```
